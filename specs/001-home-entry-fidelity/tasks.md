## Format and runtime metadata

Checklist format is `- [ ] Tnnn [P?] [USn?] Description with exact file paths`. `[P]` means a file-disjoint assignment may run with the named peer tasks **only after its listed prerequisites finish**. It does not authorize concurrent shared-tree writes. RP requires isolated branches/worktrees at the same approved base; serialize shared file integration and output journals. Unmarked tasks are serial by default.

Each task's companion metadata records `criticality`, `workload_refs`, `dominant_capability`, `change_scope`, `risk_flags`, acceptance references and explicit immediate dependencies. The feature ID plus spec/plan/task hashes recorded by the execution owner establish revision identity. Capabilities use RP vocabulary: `planning/evidence`, `fidelity-motion`, `repo-engineering`, `review-verification`, `support-mechanical`. Risk codes expand to RP flags: V=visual; M=motion/stateful; R=responsive; A=accessibility; E=evidence-sensitive; B=browser/tool-heavy; D=destructive-simplification risk. `none` means no relevant RP risk flag, not exemption from checks. All tasks are Critical except the bounded documentation synchronization T059.

Acceptance references below resolve to spec FR/SC/US scenarios, the stable check IDs in contracts/verification.md, FC TF/TR/TU obligations, and research R-decisions. Check ranges mean every named member, not a representative sample. Tests are included because spec FR-017/018, SC-001..008 and the accepted plan explicitly require deterministic and browser verification. Write behavior tests before their implementation, confirm a meaningful failing assertion once the test entry points exist, and preserve the failure; an import/tool error alone is not proof of the intended red case.
